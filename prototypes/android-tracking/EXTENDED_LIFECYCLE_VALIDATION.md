# Extended lifecycle validation (Prototype B)

**Purpose:** Document Package 2 physical-device scenarios for foreground-service restart, process death, app relaunch, and pending-event recovery.  
**Audience:** Device operators running validation on physical hardware with USB or wireless debugging.

> Synthetic fixtures for offline replay live in [fixtures/synthetic-device-db/](./fixtures/synthetic-device-db/).  
> Automated JVM/Robolectric tests do **not** substitute for these device scenarios.

---

## Evidence layers (Package 2)

| Layer | How to run | What it proves |
|---|---|---|
| **Pure JVM** | `:app:testDebugUnitTest` — `EventIngestGateTest` | Schema gate logic without Android framework |
| **Robolectric** | `:app:testDebugUnitTest` — `SessionManagerTest`, `ProcessRecreationTest`, `SqliteEventBufferTest`, etc. | Session prefs, idempotency, SQLite persistence, sequence restore |
| **Physical device** | [scripts/run-package-2-device-validation.ps1](./scripts/run-package-2-device-validation.ps1) `-Execute` | FGS, notifications, OEM task removal, screen off, adb kill/recovery |
| **Not simulatable** | Manual operator steps only | Force-stop UX, reboot + wireless adb repair, controlled movement |

Machine-readable device output: [device-validation/package-2-validation-summary.json](./device-validation/package-2-validation-summary.json) (generated by harness; safe to commit summary only — not raw logcat with sensitive research exports).

Legacy skeleton: [scripts/run-lifecycle-validation.ps1](./scripts/run-lifecycle-validation.ps1) (scenarios A–D only).

## Prerequisites

- Debug APK installed: `com.milerecover.prototype.androidtracking`
- USB or wireless debugging enabled
- [scripts/run-package-2-device-validation.ps1](./scripts/run-package-2-device-validation.ps1) reviewed

- **Never** use real routes or private coordinates in validation evidence

## Package 2 scenario map (A–J)

| ID | Title | Harness | Pass signals |
|---|---|---|---|
| **A** | Clean start | `pm clear` + launch | `session_requested` false; pending 0 |
| **B** | Start lifecycle | UI start + prefs/logcat | FGS process + notification; `SERVICE_*` state |
| **C** | App background | HOME + 15s wait | Session still requested; service survives |
| **D** | Screen off/on | `KEYCODE_POWER` toggle | Session still requested after wake |
| **E** | Task removal | `am stack remove` + manual note | Document OEM behavior; not force-stop |
| **F** | Ordinary process death | `am kill` + relaunch | Buffer counts retained; recovery events optional |
| **G** | Pending-event recovery | kill + relaunch + ack | Pending monotonic; ack → 0 |
| **H** | Idempotent start/stop | duplicate UI taps | Final `STOPPED`; `session_requested` false |
| **I** | Reboot preparation | **blocked** in harness | Manual only — post-reboot evidence required |
| **J** | Battery optimization | detect only | Record whitelist/restricted; do not change settings |

Run all scenarios:

```powershell
cd prototypes/android-tracking
.\scripts\run-package-2-device-validation.ps1 -Execute
```

## Scenario A — Clean start (Package 2)

**Hypothesis:** After `pm clear`, operator UI shows no active session and zero pending events.

1. Run harness scenario **A** (or `adb shell pm clear` + launch).
2. Capture UI dump / status snapshot.

**Pass signals:** `FGS session requested: false`; `Pending events: 0`.

---

## Scenario B — Start lifecycle (Package 2)

**Hypothesis:** Validation session starts FGS with notification and requested session state.

1. Grant foreground permissions (harness uses `pm grant` on debug builds).
2. Tap **Start validation session**.
3. Collect prefs, logcat, notification dump.

**Pass signals:** `session_requested` true; tracking state `SERVICE_*`; notification present.

---

## Scenario C — App background

**Hypothesis:** Foreground service remains active when app is backgrounded.

1. With active session, send HOME.
2. Wait ≥15s.
3. Relaunch and verify session + service.

**Pass signals:** Session still requested; process/notification observable.

---

## Scenario D — Screen off/on

**Hypothesis:** Session survives screen off interval.

1. Toggle screen off/on via adb where safe.
2. Relaunch operator UI.

**Pass signals:** Session still requested.

---

## Scenario E — Task removal (legacy: FGS restart after swipe-away)

**Hypothesis:** Task removal behavior is OEM-dependent; distinguish from force-stop.

1. Attempt task removal (`am stack remove` or manual recents swipe).
2. Document whether session/FGS survives.

**Pass signals:** Documented behavior; may require manual recents evidence on Samsung/OEM devices.

---

## Scenario F — Ordinary process death (legacy: adb kill)

**Hypothesis:** SQLite buffer + prefs survive ordinary process death (`am kill`, not force-stop).

1. Start session; note buffer/pending counts.
2. `adb shell am kill com.milerecover.prototype.androidtracking`
3. Relaunch app.
4. Compare buffer counts and session prefs export.

**Pass signals:** Buffer counts retained; optional `process_recovery` event on service redelivery (`START_FLAG_REDELIVERY`).

---

## Scenario G — Pending-event recovery after relaunch (legacy D)

**Hypothesis:** Unacknowledged events remain in SQLite and appear in sanitized export.

1. Start session; ensure ≥3 pending events (pause before any ack/export pipeline).
2. Kill process (Scenario B).
3. Relaunch; pull sanitized export.
4. Compare event count to pre-death operator UI buffer count.

**Pass signals:** Event count monotonic; sequence ordering preserved; ack clears pending to zero.

---

## Scenario H — Idempotent start/stop

**Hypothesis:** Duplicate start/stop UI actions are safe.

1. Start session twice (second should toast / ignore).
2. Stop session twice.
3. Verify `STOPPED` and `session_requested` false.

**Pass signals:** Final state idle; no duplicate active session.

---

## Scenario I — Reboot preparation

**Hypothesis:** Boot recovery is evaluated honestly after reboot.

**Harness status:** **blocked** — reboot breaks wireless adb unless operator performs documented repair.

Manual steps when safe:

1. Active session; not force-stopped.
2. Reboot device.
3. Restore adb; export sanitized diagnostics.
4. Look for `boot_recovery_evaluated` event.

**Pass signals:** Post-reboot evidence only — never claim pass from harness dry-run.

---

## Scenario J — Battery optimization state

**Hypothesis:** Restriction state is detected and recorded without silent settings changes.

1. Run harness scenario **J** (dumpsys whitelist + power save hint).
2. Optionally run restricted vs unrestricted sessions manually in settings.

**Pass signals:** JSON evidence file; `battery_status_changed` events during session.

---

## Force-stop boundary (manual / runbook §11)

Not automated in Package 2 harness (distinct from scenario F process death):

1. Start session.
2. `adb shell am force-stop com.milerecover.prototype.androidtracking`
3. Reopen app manually.

**Pass signals:** Documented behavior matches [README.md](./README.md) known limitations.
